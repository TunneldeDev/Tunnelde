# 版本与发布规则

`dev` 是默认贡献分支，`main` 保存经过审查的正式版本。自动生成的发布 PR
保留开发分支上的原始提交；所有必需检查通过后，以 **Create a merge commit** 合并。

## 公测版本

- 只使用 `vX.Y.Z-beta.1` 到 `vX.Y.Z-beta.9`，**不得发布 beta.10 或更大的公测编号**。
- 每个目标正式版本独立计数。发布 `v0.28.0` 后，下一个补丁周期从
  `v0.28.1-beta.1` 开始；下一个次版本周期则从 `v0.29.0-beta.1` 开始。
- 在需要第十个公测版本之前，审查并发布正式版。达到上限后，脚本会在创建
  快照提交、tag 和草稿之前停止，不会自动把尚未完成的开发内容发布为正式版。
- 收尾期间需要继续测试时使用 `pnpm build:local` 在本地构建，不消耗公测编号。
- 构建失败仍保留已占用的 tag；重试应复用同一份不可变源码和 tag。
  `beta.9` 可以重试，不需要分配新编号。
- 不得通过删除 tag 重置计数，不使用数字前导零、紧凑的 betaNN 格式，
  也不得把旧安装包改名冒充另一个版本。

手动 tag 发布、草稿恢复和最终发布执行相同限制。历史版本仍可被识别、比较及
用于更新发现，即使它们的格式已不允许新发布。正式版 `0.28.0` 高于已经安装的
`0.28.0-beta.9`、`.10` 和 `.11`，正式与公测更新渠道都能提供该正式版。
切换渠道不会自动降级已经安装的较新版本。

## 本地测试与正式发布

停止发布 Nightly：不再提供定时或手动 Nightly 工作流，发布入口也会拒绝创建、
恢复或公开 Nightly。开发测试使用本地构建。历史 Nightly 版本号仍可识别和比较，
以兼容已有安装和更新记录。

构建过程先使用暂存草稿，四个桌面目标、签名与 `latest.json` 全部验证通过后
才公开。Beta 公开为预发布版本，只有当前正式版设置为 Latest。
软件更新按完整语义版本比较已获取的各页结果，不依赖 GitHub 页面显示顺序或字符串排序。

安装包、自动更新包及签名文件均在文件名中包含版本号，例如
`Tunnelde_0.29.0-beta.4_aarch64.app.tar.gz` 和对应的 `.sig`。
更新清单 `latest.json` 保留固定名称，清单内的链接指向带版本号的实际文件。
GitHub 自动提供的 Source code 下载项由平台生成。

通常保留不可变的发布历史。确需清理或重发时，须有明确授权，先备份 Release 元数据
与 tag 历史，核对替代源码后再删除被替代的下载；从该源码重新构建安装包，验证完成后
再公开，不得把旧安装包改名冒充替代版本。同号重发属于维护例外，不能用来重置公测计数。
已经安装同号或更高版本的用户需要手动安装，更新器不提供同号更新或自动降级。
删除远端 tag 不会改变用户已安装软件中记录的版本号。

工作流触发与恢复步骤见[发布操作说明](releases.md)。

软件更新只提供正式版和公测版，不提供 Nightly 开发快照。
历史 Nightly 渠道设置会自动迁移为正式版。
