# 发布运维

[English](releases.en-us.md)

## 分支与常规流程

`dev` 是默认分支和贡献目标，`main` 是稳定分支。两者均要求通过 PR、解决审查讨论，并通过前端、Rust、Windows/macOS 应用、仓库及策略检查。`dev` 要求线性历史；普通工作可 squash 合并，也可 rebase 合并以保留有意义的独立提交。只有自动生成的发布推进 PR 指向 `main`，且只能使用 **Create a merge commit**。

1. 推送 `dev` 会运行 CI 和 **Development**。自动化读取实际的 `dev`、`main` 引用，并根据 `main` 上 `.github/release-source.json` 记录的上次推进的 `dev` 提交收集后续变更。`dev` 不需要包含 `main` 的发布提交。
2. 自动创建或刷新唯一的 `release/dev-to-main` PR。其文件树基于 `dev`，另有同步后的版本、源码标记和新的 CHANGELOG 章节。最终准备提交以当前 `main` 和 `dev` 为两个父提交，既保留原始 `dev` 提交及 SHA，也满足严格的分支保护。生成分支可通过强制更新重建，但不会强制更新 `dev`、`main` 或已有标签。
3. 推送 `dev` 不会发布安装包。通过 **Prepare Beta → Run workflow** 选择当前 `dev` 快照，在隔离提交中同步六处桌面版本和 CHANGELOG，再创建下一个不可变的 `vX.Y.Z-beta.N` 标签。Beta 是明确选择的测试里程碑。
4. **Publish version** 监听 `push.tags: ["v*"]`。稳定标签发布稳定版，Beta 标签发布预发布版。直接推送标签前，版本清单和发布说明必须一致，源码也必须属于正确的分支历史；支持轻量及附注标签。`GITHUB_TOKEN` 创建的标签不会触发 push 工作流，因此自动化会使用准确标签显式调度同一发布器。已经公开的标签不会重复构建。
5. 在发布 PR 中审查版本及 CHANGELOG，然后使用 **Create a merge commit** 合并到 `main`。**Stable release** 验证已审查的父提交和文件树，为准确的合并提交打标签；**Publish version** 构建 Windows、Linux、Apple Silicon 和 Intel macOS 安装包。
6. 所有构建先共享一个暂存草稿。全部桌面资源、签名及 `latest.json` 验证成功后才公开。标题使用完整版本标签，例如 `v0.28.0-beta.3` 或 `v0.27.1`。Beta 固定使用 `prerelease: true` 和 `make_latest: false`；稳定版使用 `/releases/latest/`，恢复较旧稳定版本不能将该指针倒退。历史 Release 和不可变标签保留。
7. 准备稳定标签后，刷新开发自动化以处理推进后累积的工作；没有新变更时不会创建重复发布 PR。

## 本地开发构建

Nightly 发布已停用，不存在定时或手动触发的 Nightly 工作流；共享发布器也会拒绝 Nightly 标签，包括恢复历史草稿的尝试。使用 `pnpm build:local` 测试开发改动，无需创建公开标签或 Release。历史 Nightly 版本元数据仍可读取以保持兼容。

## 版本与 CHANGELOG

`feat` 增加次版本号；其他开发变更，包括文档、CI 和测试，增加修订版本号。使用 `!` 或 `BREAKING CHANGE:` 标记的不兼容变更，在 1.0 之前增加次版本号，在 1.0 之后增加主版本号。发布提交不计入摘要，一批变更采用其中最高的升级幅度。显式 Beta 使用同一个下一稳定版本作为基础，并附加唯一序号。

后缀采用 **`beta.N`，其中 N 为 1 至 9**，不要发布 `beta.10` 或更高。例如先发布 `0.28.0-beta.1`、`0.28.0-beta.2`，再发布稳定版 `0.28.0`；下一目标版本的首个 Beta 为 `0.28.1-beta.1`。在需要第十个里程碑前，应审查并发布稳定版推进 PR。若尚未达到发布条件，应继续修复，并使用本地构建进行中间测试；自动化会停止，不会发布未经审查的稳定版或重复使用序号。

序号分配读取标签，不使用工作流运行次数或显示标题。失败的构建也会占用序号；重试允许的相同源码和标签时会复用草稿，包括 beta.9。历史格式仍可读取并占用其原序号，但不能违反当前策略重新发布或恢复。新的目标版本从 beta.1 开始。

更新会跨所有页面比较语义版本，Beta 渠道也包含稳定版，因此使用历史 `0.28.0-beta.10` 或 `.11` 的用户可以直接更新到 `0.28.0`，无需兼容构建。不要只重命名 Release 或标签，而保留内嵌不同版本的二进制文件。例外的清理或重发需要明确授权、备份元数据和标签历史、验证替代源码，并重新验证安装包。同版本替换或降级需要手动安装；更新检查仍执行正常的版本和签名检查。常规发布保留历史，不移动已有标签。

版本策略另见 [English](versioning.en-us.md) 和[简体中文](versioning.zh-cn.md)。

六处桌面版本位置必须同步：`package.json`、Tauri 配置、桌面 Cargo 清单及锁文件、兼容用途的 `.release-please-manifest.json` 和 `CITATION.cff`。原 Release Please action 已由仓库脚本替代，清单继续保留为版本元数据。

CHANGELOG 包含双语分类、亮点、可展开详情、PR/提交链接和贡献者。同名标题保留各自的来源和作者，`main` 上的历史逐字节保留。自上次推进的 `dev` 源码以来新编辑的可选 Unreleased 说明会成为本次亮点；未变更的旧摘要会被忽略，防止旧周期描述新版本。没有新摘要时，亮点由当前变更生成。在输入和日期固定时生成结果确定，不依赖 AI 服务，且在修改 `main` 之前就写入 PR。PR 正文保持简洁并指向准确的 CHANGELOG SHA。

不要直接编辑 `release/dev-to-main`；修复和版本策略变更应通过 `dev`。自动化更新生成分支前重新检查实际引用，避免旧 PR 基础快照遗漏新变更。如果 `main` 在生成发布元数据之外有改动，自动化会拒绝覆盖；应先通过审查后的 PR 将热修复合并回 `dev`。

## 凭据与保护

使用短期仓库 `GITHUB_TOKEN`，并在 **Settings → Actions → General → Workflow permissions** 中启用 **Allow GitHub Actions to create and approve pull requests**。不需要 PAT、App 密钥、组织级访问或规则集绕过；各工作流分别声明所需权限。自动化可以创建 PR，但不会批准或合并 PR。

自动化将 PR 策略状态写到实际 head。GitHub 可能将机器人创建的 PR 的 `pull_request` CI 标为等待运行审批（`action_required`）。维护者审查生成的差异和准确 head SHA 后，从 PR 的 **Checks** 或对应 Actions 页面批准该次运行，等待该 PR 运行的必需检查通过再合并。批准工作流运行表示允许其代码执行，与批准或合并 PR 是不同的操作。

Development 会在工作流提示中给出 PR 编号和准备好的 SHA。它不会批准自己的 PR 运行，也不会额外调度整组 CI。单独手动运行 CI 不能解除 PR 运行的审批等待。如果 dev 更新后发布 head 已替换，应重新审查并批准新 head 对应的运行，旧提交的成功结果不够。高权限策略工作流只执行受信任目标分支的策略代码，不检出贡献代码；必需检查仍绑定到 Actions。

`.github/main-ruleset.json` 和 `.github/dev-ruleset.json` 是纳入版本管理的保护定义。两者均禁止删除和强制推送，要求 PR 和全部七项检查，且没有绕过主体。`.github/repository-settings.json` 记录合并方式设置：仓库层面启用 squash、rebase 和 merge commit；`dev` 规则集允许 squash/rebase 并要求线性历史，`main` 只允许 merge commit，以保留准确的 `dev` 提交。merge 和 squash 的默认提交消息均使用 PR 标题和正文。必须通过仓库设置或 API 应用设置和规则集变更，单独编辑 JSON 不会使其生效。

PR 策略按 Conventional Commits 验证标题和每个提交标题。两种贡献合并方式均受此约束，切换到 rebase 也不能引入绕过语义版本规则的消息。策略按当前 PR head 检查完整提交列表，并拒绝不完整历史，包括超过 GitHub 250 个提交列表限制的 PR。引用更新后，策略对不一致的 API 快照采用有限退避重试；重试耗尽仍不完整时拒绝。生成 PR 的检查必须对应准确准备好的 head，即使 PR 已存在，恢复流程也会重新检查策略，但不会重复调度 CI。不可变源文件读取遇到 GitHub 临时服务器错误（500、502、503、504）时最多尝试四次，间隔 1、2、4 秒；永久权限或校验错误立即失败。

生成的发布 PR 保留所有开发提交和一个准备提交。策略根据记录的 `main`/`dev` 引用检查准备提交的两个父提交，拒绝发布元数据以外的改动。即使源码标记未变化，旧的单父准备提交也会重新生成。稳定发布会拒绝对保留历史的准备提交执行 squash/rebase，也会拒绝与已审查文件树不一致的合并结果。高权限策略只读取提交元数据和可信基础分支代码，不执行贡献代码。

无论采用哪种合并方式，发布汇总都读取实际保留的提交消息，并按整个批次中的最高语义升级幅度确定版本。rebase 后的提交即使 SHA 不等于 PR 最终合并 SHA，也会关联到已合并 PR。CHANGELOG 保留独立标题、PR/提交链接、原提交作者、PR 作者及识别到的共同作者标记。

## 构建失败与恢复

中断的构建会留下草稿和不可变标签。从包含当前工作流的分支运行 **Release**，将 `existing_tag` 设为原标签。工作流重新构建该标签源码，所有构建器共享草稿，验证每项资源后自动发布。准备步骤会拒绝已公开的 Release；恢复不会替换公开安装包。不要移动已有标签或重复使用废弃版本。

发布会检查标签的不可变提交、渠道和分支祖先关系。构建期间 `dev` 前进不会使选定快照失效，也不会使已完整的草稿无法发布；从分支历史移除的源码会被拒绝。历史 Beta 发布不能覆盖稳定版或更新版本的安装包；恢复较旧稳定版时明确保持较新的稳定版为 latest。

**Publish version → Run workflow → tag** 也可为已有版本标签验证并创建缺失草稿；**Release → existing_tag** 恢复已暂存的草稿。两者均保留原源码，不修改标签或重新构建已公开的包。Development 并发控制仅串行化发布 PR 维护；Beta 和版本发布有独立工作流组。

编译器计时只作为可选 Actions 构建产物。原生辅助程序由 Tunnelde-agent 仓库独立版本化、构建和发布；插件市场仓库也有独立发布流程。辅助程序不会出现在桌面 Release 下载中。

Rust 缓存恢复是可选的：每个步骤最长三分钟，缓存下载的分段超时为两分钟。恢复失败或超时时，一次性托管 runner 会删除受影响的 target 目录及 Cargo registry/Git 缓存，再从源码编译；保留源码、其他 Rust 工作区和已安装工具链。恢复旧发布标签时，从工作流源码加载该清理工具，但仍构建不可变标签。手动 **Release** 恢复还提供 `use_rust_cache: false`，可在缓存服务故障时从源码编译，无需更改源码标签或缓存命名空间。

贡献 CI 可以恢复共享缓存，但只有 `main`/`dev` 运行会保存缓存，避免为 PR 创建重复缓存归档。私有局域网代理地址应保留在本地开发设置中；托管 runner 需要自己的可达网络路径。

## 应用内渠道、来源与 OTA

更新位于**设置 → 更新**。状态栏通知、托盘操作和命令面板都进入同一设置分区，不创建独立更新页面。默认每天检查一次，也可选择每次启动或每周检查；检查不会自动下载或安装。发布说明包含在 `latest.json` 中，并以可折叠 Markdown 显示。

- **正式版**使用最新公开稳定版清单，排除预发布版。
- **公测版（Beta）**在带有 `latest.json` 的已发布稳定版和 Beta 中选择最高版本。
- Nightly 发布已停用，也不是应用内更新渠道。旧 Nightly 偏好迁移到正式版；正式版和 Beta 发现逻辑排除每日快照。
- 发现逻辑遍历 GitHub Release 分页并按 SemVer 比较，不依赖标题或列表顺序。草稿、不完整 Release 和预发布标记不匹配的条目会被排除。来源不可用视为错误，不会误报已是最新；API 发现最多读取十页。
- GitHub API 限流或不可用时，Beta 检查通过相同配置代理使用公开 Atom feed 中最近的已发布版本。后备源覆盖最近条目而非完整历史；它按 SemVer 比较，并以 `latest.json` 验证选定标签，跳过清单返回 404 的过期条目。网络错误或无效清单仍会使检查失败，不会关闭 HTTPS、版本检查或安装包签名验证。超时、连接和 API 配额失败分别显示不同消息。
- 切回正式版不会自动将较新的预发布版降级，而是等待高于当前安装版本的稳定版。更改来源或渠道会使先前的更新选择失效，安装期间不能更改。

全新安装始终默认正式版，包括 Beta 构建；公测版需要用户主动选择，不提供开发快照。已有正式版/Beta 偏好保留，旧 Nightly 偏好迁移到正式版。

官方来源为 **GitHub**，不内置第三方镜像。**自定义 HTTPS 来源**可以按 `https://updates.example.com/{channel}/latest.json` 这样的模板提供标准 Tauri 更新清单。占位符必须在路径中恰好出现一次，展开为 `stable` 或 `beta`；拒绝凭据、查询字符串和片段。Beta 检查并发查询稳定版和 Beta，并选择符合条件的最新版本；不可用渠道可以返回 HTTP 204。其他请求端点仍须可达。这是清单服务，而不是通用 GitHub 代理前缀。

镜像维护者应在发布后才复制已验证的 `latest.json` 和对应签名更新包，保留版本、签名和发布说明，并将包 URL 改为镜像 HTTPS 地址。原子发布清单可避免向用户提供未完成的更新。镜像数据不会替换应用内嵌的验证密钥。网络设置中的应用更新代理适用于来源发现、清单和安装包下载；自定义来源本身不是代理设置。

`requireSignedVersion` 还会将声明版本绑定到已签名安装包，防止镜像以新版本清单重放旧签名安装包。可信签名注释中不含版本的旧包需要手动更新。

现有发布流程已为 Windows 和 AppImage 安装提供**带签名的完整安装包 OTA 更新**。安装会保留检查时选中的准确安装包、验证签名并重启应用。检查和安装共享互斥操作保护，进度事件会节流，避免淹没界面。这不是二进制差量补丁；当前更新器不需要额外差量格式。未签名的 macOS 和 Linux 系统包仍可检查所选渠道并打开对应 Release 手动安装；开发构建不自更新。
