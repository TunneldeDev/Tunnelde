本页是当前 rollout 的可执行长期计划。工作合入、CI 完成、验收检查执行或 Release 公开后，
应及时更新本页。

Issue #468 是长期验收 Issue。它的正文和早期评论是历史交付日志，不是当前状态页；当前执行

## 执行规则

- 状态统一使用 `已完成`、`进行中`、`受阻`、`待开始`。只有精确 head 的必需 CI 通过并记录
  验收证据后，PR 才算完成。
- P0/P1 问题阻断发布；主流程可用时，P2 精修可以留到后续版本。
- 每完成约一至三个连贯功能发布一次 Beta。正式版必须绑定同产品源码、已发布且明确验收的
  Beta。
- 开发继续期间，自动生成的 `release/dev-to-main` PR 保持 Draft。只有最终审查过的 head
  才转为 Ready for review，并由该操作启动准确 head 的 PR CI。不得用一次手动 CI 运行替代
  这个生命周期。
- 任何必需验收项未完成时，不得关闭 Issue #468，也不得宣称 rollout 已完成。

## 发布 PR 生命周期

1. 开发自动化创建或刷新 `release/dev-to-main` 时保持 Draft。
2. Draft 刷新不运行完整应用 CI 矩阵，避免每次开发推送都消耗一整套平台检查。
3. 发布批次最终确定后，审查准确 head，再把该 PR 转为 Ready for review。
4. 等待准确 head 的完整 PR CI 通过。不得合并过期 head，也不得绕过失败检查。
5. 使用 **Create a merge commit** 合并。正式发布对已审查的合并提交打标签，并在公开前验证
   四个桌面构建、签名和 `latest.json`。
6. 如果 PR 转为 Ready 后开发又有新提交，应先转回 Draft，再刷新分支和 head。

## 更新流程

1. PR 合入、Release 公开或出现阻断项后，立即更新对应行。
2. 记录不可变提交、CI run ID、Release 标签和验收证据，不依赖聊天记录。
3. 本页必须与 Issue #468 的最新评论保持一致。历史正文不得当作当前状态继续复制。
